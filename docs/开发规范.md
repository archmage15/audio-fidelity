# 开发规范

适用于本仓库的所有开发者和 AI 智能体（Claude Code、Codex 等）。智能体开始任何改动前必须先读完本文。

> 仓库是组织免费版的私有仓库，GitHub 无法开启分支保护，以下规则不会被平台强制执行，**全靠自觉遵守**。不确定时先停下来问，不要直接动 `main`。

## 1. 分支模型

| 分支 | 从哪里切出 | 合并到哪里 | 用途 |
| --- | --- | --- | --- |
| `main` | — | — | 稳定版本。**只接受 `develop` 和 `hotfix/*` 的合并**，任何人都不直接在 `main` 上提交 |
| `develop` | `main` | `main` | 日常集成分支，所有功能开发都汇总到这里。不直接在 `develop` 上写代码 |
| `feature/<描述>` | `develop` | `develop` | 功能开发。**一个大功能，或几个相关的小功能，开一个 feature 分支** |
| `hotfix/<描述>` | `main` | `main` **和** `develop` | 线上紧急修复。合入 `main` 后必须同步合回 `develop`，避免下次发布把修复冲掉 |

- 分支名用小写英文和连字符，简短说明做什么：`feature/invite-admin`、`feature/tingwu-asr`、`hotfix/upload-range`。
- 不相关的功能不要塞进同一个 feature 分支；一个 feature 分支做完就合并、删除，不要长期存活。
- 禁止对 `main`、`develop` 执行 `git push --force`、`git reset` 后强推或删除分支。

## 2. 开发流程

```bash
# 1) 开始前：同步 develop，从它切出功能分支
git fetch origin
git switch develop && git pull --ff-only
git switch -c feature/<描述>

# 2) 开发：每完成一个开发阶段就提交一次（见第 3 节），并及时推送
git push -u origin feature/<描述>

# 3) 完成：先同步 develop，解决冲突、跑完检查（见第 4 节）
git fetch origin && git rebase origin/develop   # 或 merge，按团队习惯
git push --force-with-lease                      # 只允许对自己的 feature 分支这样做

# 4) 发 PR 合入 develop，合并后删除功能分支
gh pr create --base develop --title "<概括>" --body "<做了什么、为什么、怎么验证的>"
```

- **开始写代码前先看当前分支**：如果在 `main` 或 `develop` 上，先按上面切出 feature 分支，再动代码。
- **发布**：`develop` 达到可发布状态后，发 PR `develop → main`，合并后可在 `main` 上打标签（如 `v2026.11.10`）。
- **热修复**：

  ```bash
  git switch main && git pull --ff-only
  git switch -c hotfix/<描述>
  # 修复、提交、检查
  gh pr create --base main      # 先合入 main
  gh pr create --base develop   # 再合回 develop（或合并 main 后把 main 合进 develop）
  ```

- PR 用合并提交（merge commit）合入，保留分支历史；不要在 PR 之外手工把分支合进 `develop` / `main`。

## 3. 提交规范

- **按开发阶段提交**：每完成一个可以独立说明的阶段（一个接口、一个页面改动、一轮修复、一次文档更新）就 commit 一次，不要让大量改动堆着不提交。只有一个阶段本身就改动了非常多文件时，才一次提交较多文件。
- 一个提交只做一件事；格式化、重命名这类机械改动单独提交。
- 提交信息：
  - 第一行简短概括做了什么（中英文均可，约 50 字符以内，不加句号）；
  - 空一行后写正文：为什么改、有什么取舍、如何验证；
  - AI 智能体在末尾按自身约定加署名行，例如 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`。
- 提交前用 `git status` / `git diff --staged` 确认内容，**不要用 `git add -A` 把不认识的文件一起提交**。

## 4. 提交 PR 前的检查

本地开发机不需要安装模型和推理依赖，用桩引擎测试即可；真实推理只在部署服务器上验证。

```bash
# 网页
cd web
python -m py_compile webapp/*.py webapp/asr_hook/*.py
node --check webapp/static/app.js
bash tests/fake_engine/make_fake_engine.sh ../engine /tmp/fake-engine   # 生成桩引擎
# 用桩引擎启动 API / Worker / 常驻推理进程后：
python tests/e2e_check.py http://127.0.0.1:<端口> --admin-code … --user-code … --user2-code …

# 引擎（需要完整环境时在服务器上跑）
cd engine && bash linux.sh check
```

PR 描述里写清楚跑了哪些检查、结果如何；没跑的要说明原因。改了前端界面的，附截图。

## 5. 代码与安全约定

- **绝不提交凭据和运行数据**：`.env`、`讯飞配置.json`、`听悟配置.json`、SSH 密钥、邀请码、模型文件、录音、缓存、评测输出。`.gitignore` 已覆盖这些路径，不要用 `git add -f` 绕过。
- **不读取、不打印凭据的值**：排查配置问题时只检查文件是否存在、字段是否齐全、格式（长度、字符类型），不输出具体内容。
- **网站不改引擎源码**：`web/` 通过 `ENGINE_ROOT` 调用 `engine/`，需要改变引擎行为时用 `web/webapp/asr_hook/`、`web/webapp/engine_server.py` 里的钩子实现。确实要改引擎本身时，在独立的提交里改 `engine/`，并说明对网站的影响。
- `engine/` 和 `web/` 的改动尽量分开提交。
- 改了接口、环境变量、部署方式，同一个分支里同步更新 `web/docs/API.md`、`web/docs/DEPLOY.md`、`web/.env.example`。
- 生产服务器上的操作（部署、重启服务、改配置）属于对外操作，执行前先确认已获授权。
